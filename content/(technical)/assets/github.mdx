Nox can expose mods that live on **GitHub** instead of uploading them. The `github` provider is
**read-only** and handles **mods only**: it reads a manifest from the repository, turns GitHub
**releases** into Nox releases, and **redirects downloads to GitHub**. Nox stores no bytes.

## Repository requirements

### `nox.mod.json` at the repository root

```json title="nox.mod.json"
{
  "type": "mod",
  "id": "nox.network",
  "provides": ["fr.hactazia.network", "network"],
  "name": "Network",
  "description": "A networking API for Nox.",
  "license": "GPL-3.0",
  "icon": null,
  "tags": ["usr:network"],
  "authors": [{ "name": "Hactazia", "email": "hactazia@gmail.com" }],
  "contact": { "source": "https://github.com/AtelierVR/nox.network" }
}
```

| Field | Required | Used as |
|---|---|---|
| `id` | yes | asset `name` (its identifier) |
| `type` | yes | must be `"mod"` |
| `name` | yes | asset `title` |
| `description` | yes | asset `description` |
| `license` | yes | metadata |
| `authors` | yes | metadata (`[{ "name": … }]`) |
| `icon` | no | asset image (URL, or `null` for none) |
| `provides` | no | asset aliases |
| `tags` | no | asset tags — only those containing `:` are kept |

Any other field (`version`, `entrypoints`, `relations`, `constraints`, …) is accepted and ignored.

### A `manifest.json` asset on each release

```json title="manifest.json"
{
  "version": "1.0.9",
  "files": [
    {
      "url": "https://github.com/AtelierVR/nox.network/releases/download/v1.0.9/nox.network-1.0.9-windows.zip",
      "platforms": ["windows"],
      "hash": "sha256:d3658cb763479d612bde2ab1752821b8c2342cc5b68f8696ed02e3e1e011e933",
      "size": 88941
    }
  ]
}
```

- `url` **must** point to `https://github.com/{owner}/{repo}/releases/download/…`; any other host is rejected (`502`).
- The file name and its MIME type are taken from the GitHub asset that matches the URL (`.zip` → `application/zip`).
- Each `platforms` entry becomes a `platform` attribute, so `?platform=windows` filters work.
- `hash` must be `algo:hex` (e.g. `sha256:…`).

## Releases

Only **published** releases are exposed. Drafts — builds still running in GitHub Actions — are
ignored until published.

| Nox release | From GitHub |
|---|---|
| `name` | release tag (`v1.0.9`) |
| `title` | manifest `version`, or the release name/tag |
| `changelog` | release body |
| `channel` | `stable`, `nightly` (tag contains `nightly`) or `candidate` (pre-release) |
| `status` | always `completed` |

A release published without `manifest.json` is still listed, but its file listing is empty.

Everything this provider serves is **published content**, so it is always `completed`: there is no
pending state to wait for. A `?status=` filter that does not include `completed` therefore returns
nothing — see [Download](/docs/assets/download).

## Configure

```yaml
github:
  repositories:
    - 1132335750             # GitHub repository id — not "owner/repo"
  token: '${GITHUB_TOKEN}'   # optional, raises the API rate limit
  api_base: 'https://api.github.com'
  cache_ttl: 300             # seconds
```

Environment variables: `GITHUB_REPOSITORIES` (comma-separated ids), `GITHUB_TOKEN`,
`GITHUB_API_BASE`, `GITHUB_CACHE_TTL`.

The id is the numeric `id` returned by `GET /repos/{owner}/{repo}` (it also appears in the
`release-assets.githubusercontent.com` URLs). Every configured repository is imported as a mod
asset at startup.

## Read

Imported mods are served by the regular mod endpoints — see the API reference for
[search](/api/mod/search), [get asset](/api/mod/get-asset), [list releases](/api/mod/list-releases),
[get release](/api/mod/get-release), [list files](/api/mod/list-files) and [get file](/api/mod/get-file).

`{id}` accepts the Nox asset id, the manifest `id`, a `provides` alias, **or the numeric GitHub
repository id** — so a repository can be read without importing it first.

`{version}` accepts the tag (`v1.0.9`, or `1.0.9`) or the numeric GitHub release id.

<Callout type="info">
`GET /api/mods/{id}/releases/{version}/files/{name}` answers `302` and redirects the client to
`github.com/.../releases/download/...`. The bytes are never proxied, so the repository must stay
publicly downloadable.
</Callout>

## Refresh

GitHub API responses are cached for `cache_ttl` seconds — including `404`s. To invalidate the cache
on demand, call the [webhook route](/api/mod/webhook-post):

```bash
curl -X POST "https://{server}/api/mods/{id}/webhook?token=$WEBHOOK_TOKEN"
```

- The token is generated by Nox (32 random bytes hex, stored as `webhook_token` in the asset record) — it is **not** a GitHub secret.
- The request body is ignored and no signature is verified: the call only drops the cached repository, manifest and release data, then answers `204`.
- GitHub cannot send custom headers, so the token goes in the query string (the `X-Nox-Webhook-Token` header also works).

## Limitations

- **Mods only** — worlds and avatars have no GitHub provider.
- **Read-only**: deletion, release/file upload and asset images are not supported for GitHub assets (`501`). The upload routes always target the upload provider.
- Imported mods have no Nox owner: `owner` and `contributors` are placeholders.
- Anonymous GitHub API calls are rate-limited; Nox reports it explicitly when the limit is hit — set `github.token` to avoid it.
